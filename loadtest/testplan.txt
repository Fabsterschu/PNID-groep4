
Grafana k6 gebruikt JavaScript om gebruikersgedrag te stimuleren. Met Virtual Users kunnen meerdere gebruikers tegelijkertijd HTTP-verzoeken naar een applicatie versturen. Met k6 meten we vervolgens onder andere responstijden, foutpercentages en het aantal request 
 
Locale integratie test:
T1: node server.js
T2: Invoke-WebRequest -Uri "http://127.0.0.1:3000/"
Resultaat: statuscode 200  (OK), (De Node-server serveert de homepage via HTTP) Met Grafana k6 hebben we een HTTP-request vanuit een Docker-container verstuurd. De server antwoordde met statuscode 200. k6 meet automatisch onder andere de responstijd, het aantal requests en het percentage mislukte requests. Deze metrics gebruiken we om de prestaties van onze applicatie bij toenemende belasting te onderzoeken.

Locale K6 Loadtest: Onze traffic generator maakt gebruik van een ramping-arrival-rate scenario. Hiermee verhogen we gecontroleerd de hoeveelheid HTTP-verkeer. We beginnen met een lage belasting, verhogen deze geleidelijk en bouwen daarna weer af. Zo kunnen we onderzoeken hoe de applicatie reageert op veranderende belasting 
T1: node server.js
T2:Get-Content -Raw .\loadtest\traffic.js | docker run --rm -i -e TARGET_URL="http://145.52.126.137/" grafana/k6:latest run -
Onze k6 traffic generator draait in een Docker-container en stuurt HTTP-requests naar de Node.js-backend van TropoMetrics. 
Hiermee kunnen we gecontroleerd belasting genereren en de prestaties van de applicatie meten 
 
HPA horizontal pods autoscaler en CPU-metrics controleren:
T1: kubectl run -i --tty load-generator --rm --image=busybox:1.28 --restart=Never -- /bin/sh -c "while true; do wget -q -O- http://tropometrics-service; done"
CPU vermogen wat wordt gebruikt, hoeveelheid replicas, blijft replicas maken als cpu vermogen meer dan 50% wordt gebruikt. Tot max pods is bereikt die is  nu ingesteld op 10.
T2: kubectl get hpa -w
T3: kubectl get pods -o wide --watch
laat zien containers aanmaken, pods updates, verdeeld over nodes
