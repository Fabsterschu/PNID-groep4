TROPOMETRICS - TESTPLAN MET COPY-PASTE COMMANDO'S
Datum demonstratie: 9 november 2026
Omgeving: Windows PowerShell, Node.js, Docker Desktop, Grafana k6 en Kubernetes

BELANGRIJK

Voer de commando's uit in de hoofdmap van het project (waar server.js staat).

Kopieer alleen de regel onder COMMANDO, niet de toelichting.

Open voor tests met meerdere terminals een nieuwe terminal in VS Code.

Gebruik NAMESPACE niet letterlijk: vervang het door de echte Kubernetes-namespace.

Je eigen kubectl heeft nog geen kubeconfig. De Kubernetes-tests kunnen pas met een
werkende kubectl-context (bij jou of je teamgenoot).

Stuur de loadtest alleen naar jullie eigen website. Belast niet onbedoeld de
externe Open-Meteo-API of andere websites.

TEST 00 - INSTALLATIE EN TESTBESTAND CONTROLEREN
Wat testen we? Of Docker, k6 en je loadtestbestand beschikbaar zijn.

COMMANDO 1:
docker version

COMMANDO 2:
docker run --rm grafana/k6 version

COMMANDO 3:
Test-Path .\loadtest\traffic.js

Verwacht: Docker geeft versie-informatie, k6 toont een versie en Test-Path
geeft True terug.
Betekenis: De generator is klaar om scripts te draaien.
Toelichting: --rm verwijdert de tijdelijke Docker-container na afloop.

TEST 01 - UNIT TESTS (ALS ZE BESTAAN)
Wat testen we? Losse JavaScript-functies zonder webserver.

COMMANDO:
npm run

Controleer of in de uitvoer een script met de naam test staat.
ALLEEN als dit script bestaat:
npm test

Verwacht: De bestaande unit tests slagen.
Betekenis: De geteste losse functies geven de juiste uitkomst.
Let op: Bestaat geen testscript? Noteer dan 'niet ingericht'. k6-checks zijn
geen unit tests.

TEST 02 - LOKALE INTEGRATIETEST
Wat testen we? Of Node.js/Express en de website samenwerken.

TERMINAL 1 - COMMANDO:
node server.js

TERMINAL 2 - COMMANDO:
Invoke-WebRequest -Uri "http://127.0.0.1:3000/"

Verwacht: StatusCode 200.
Betekenis: De Node-server serveert de homepage via HTTP.
Als je API afzonderlijk wilt controleren, doe dan eerst een geldige aanvraag
volgens de vereiste queryparameters van /api/v1/data.

TEST 03 - LOKALE LOADTEST MET K6
Wat testen we? Of k6 gecontroleerd verkeer naar de lokale Node-server stuurt.

TERMINAL 1: laat node server.js aan staan.
TERMINAL 2 - COMMANDO:
Get-Content -Raw .\loadtest\traffic.js | docker run --rm -i -e TARGET_URL="http://host.docker.internal:3000/" grafana/k6 run -

Verwacht: http_reqs > 1, de checks slagen, bij voorkeur 0% fouten.
Betekenis: De loadgenerator werkt en de lokale app verwerkt de requests.
Belangrijk: Dit bewijst nog GEEN HPA-opschaling; Kubernetes wordt niet belast.

Eerder lokaal gemeten: 435 requests, 435 geslaagde checks, 0 fouten,
gemiddelde http_req_duration 5,93 ms en p95 8,81 ms.

TEST 04 - SMOKE TEST VAN DE ONLINE WEBSITE
Wat testen we? Of het webadres van Kubernetes bereikbaar is.

COMMANDO:
Get-Content -Raw .\loadtest\traffic.js | docker run --rm -i -e TARGET_URL="http://145.52.126.137/" grafana/k6 run --once -

Verwacht: checks_succeeded 100%, HTTP status 200, http_req_failed 0%,
http_reqs 1.
Betekenis: De online website reageert succesvol op een enkel HTTP-verzoek.
Dit zegt NIET dat de nieuwste code draait of dat Pods automatisch schalen.

Eerder gemeten: 1 verzoek, HTTP 200, 0 fouten, 2,43 ms.
Een weergegeven snelheid zoals 148 req/s is slechts een momentberekening;
er zijn werkelijk maar 1 request uitgevoerd.

TEST 05 - CLUSTERTOEGANG CONTROLEREN
Wat testen we? Of kubectl het bestaande cluster kan bereiken.

COMMANDO 1:
kubectl config current-context

COMMANDO 2:
kubectl get namespaces

COMMANDO 3:
kubectl get nodes

Verwacht: Er is een context ingesteld, namespaces worden getoond en nodes
zijn bereikbaar.
Betekenis: Je kunt de live Kubernetes-omgeving uitlezen.
Als current-context 'not set' geeft, heb je een kubeconfig van je teamgenoot
of beheerder nodig. Alleen een VPN-verbinding is niet voldoende.

TEST 06 - JUISTE DOCKER-IMAGE EN WEBSITEVERSIE
Wat testen we? Of Kubernetes de NIEUWSTE TropoMetrics-code heeft uitgerold.

COMMANDO 1:
kubectl get deployment tropometrics-deployment -n NAMESPACE -o wide

COMMANDO 2:
kubectl rollout status deployment/tropometrics-deployment -n NAMESPACE

COMMANDO 3:
kubectl get pods -n NAMESPACE -l app=tropometrics -o wide

Verwacht: De Deployment is Ready, Pods draaien en de image-tag/digest komt
overeen met de nieuw gebouwde versie. Controleer ook een herkenbare nieuwe
wijziging op de website.
Betekenis: De volgende tests raken echt de juiste applicatieversie.
LET OP: Bij imagePullPolicy IfNotPresent kan tropometrics een oude
image blijven. Gebruik in jullie bestaande deploy-proces bij voorkeur een
unieke versie-tag en controleer die achteraf.

TEST 07 - HPA EN CPU-METRICS CONTROLEREN
Wat testen we? Of de autoscaler actuele CPU-waarden ontvangt.

COMMANDO 1:
kubectl get hpa tropometrics-hpa -n NAMESPACE

COMMANDO 2:
kubectl top pods -n NAMESPACE -l app=tropometrics

COMMANDO 3:
kubectl describe hpa tropometrics-hpa -n NAMESPACE

Verwacht: De HPA heeft een concrete huidige CPU-utilization in plaats
van <unknown>; top pods toont CPU-waarden.
Betekenis: De HPA kan de belasting meten en besluiten om te schalen.

Instellingen uit app.yaml:

minReplicas: 2

maxReplicas: 10

CPU-request per applicatie-Pod: 100m

CPU-target HPA: 50% van de request, gemiddeld circa 50m CPU per Pod.

CPU-HPA gebruikt normaal metrics-server voor de resource-metrics.
Prometheus bewaart monitoringdata; Grafana maakt daarvan grafieken.

TEST 08 - HPA SCALE-UP DOOR K6-LOADTEST
Wat testen we? Of meer HTTP-verkeer leidt tot hogere CPU-belasting en
automatisch extra applicatie-Pods.

TERMINAL 1 - COMMANDO (MET CLUSTERTOEGANG):
kubectl get hpa tropometrics-hpa -n NAMESPACE -w

TERMINAL 2 - COMMANDO (MET CLUSTERTOEGANG):
kubectl get pods -n NAMESPACE -l app=tropometrics -w

TERMINAL 3 - COMMANDO (K6 OP JE EIGEN LAPTOP):
Get-Content -Raw .\loadtest\traffic.js | docker run --rm -i -e TARGET_URL="http://145.52.126.137/" grafana/k6 run -

Verwacht: k6 voert meerdere verzoeken uit. Als de CPU-belasting voldoende
lang boven het HPA-doel blijft, kan het gewenste aantal Pods stijgen van
2 richting maximaal 10.
Betekenis: Stijgt het aantal Ready Pods, dan is opschalen aangetoond.
Als er geen Pods bijkomen en CPU blijft onder het doel, is de belasting
waarschijnlijk te licht; dat is geen bewijs dat de HPA defect is.

Huidige traffic.js: ramping-arrival-rate, oplopend naar 1, 5 en 10
iteraties/seconde en terug naar 0 in circa 100 seconden. Met één GET per
iteratie is dat ongeveer hetzelfde aantal HTTP-verzoeken per seconde.
Wijzig dit profiel niet op het gedeelde cluster zonder afstemming.

TEST 09 - PERFORMANCE EN FOUTEN TIJDENS BELASTING
Wat testen we? Of TropoMetrics tijdens toenemend verkeer bereikbaar blijft.

COMMANDO:
Gebruik dezelfde k6-commandoregel als in TEST 08. Bekijk daarna de output.

Controleer deze velden:

checks_succeeded: aantal/percentage geslaagde controles

http_req_failed: percentage HTTP-fouten

http_req_duration p(95): responstijd waaronder 95% van de verzoeken valt

http_reqs: totaal werkelijk uitgevoerde HTTP-verzoeken

dropped_iterations: geplande iteraties die k6 niet kon starten

Verwacht: Bij voorkeur 100% geslaagde status-200-checks, 0% HTTP-fouten
en geen dropped_iterations. Spreek vooraf een p95-grens af.
Betekenis: Dit laat zien hoe goed de app reageert bij belasting.

TEST 10 - SCALE-DOWN EN HERSTEL
Wat testen we? Of Kubernetes na de loadtest overbodige Pods weer verwijdert.

ACTIE:
Laat de k6-test uit TEST 08 eindigen. Laat de watch uit terminals 1 en 2
doorlopen. Noteer het aantal Pods tijdens piek en na afloop.

OPTIONEEL COMMANDO:
kubectl get hpa tropometrics-hpa -n NAMESPACE

Verwacht: De CPU-belasting daalt. Als de HPA eerst opschaalde, daalt het
aantal Pods na enige tijd weer richting minReplicas=2.
Betekenis: De HPA kan zowel opschalen als afschalen.
Let op: Standaard kan de HPA ongeveer 5 minuten wachten voor scale-down.

HTTP 200, maar oude website: controleer image-tag/digest, het buildproces
en de draaiende Pods. imagePullPolicy IfNotPresent kan een oude image houden.

HPA toont <unknown>: controleer metrics-server en kubectl top pods.

CPU lager dan 50%: dan is opschalen mogelijk niet nodig.

CPU boven doel, maar geen nieuwe Pods: bekijk kubectl describe hpa;
controleer Events, Kubernetes-capaciteit en wacht enkele meetrondes.

k6 heeft dropped_iterations: onvoldoende VUs om de geplande snelheid te halen.

kubectl maakt verbinding met localhost:8080 en weigert: kubeconfig/context
ontbreekt, ook al is OpenVPN verbonden.

(r) => r.status === 200
=> is een JavaScript-arrow function. De functie ontvangt response 'r'
en geeft true/false terug. === vergelijkt de waarde én het datatype.

export default function ()
Dit is de functie die k6 voor elke testiteratie uitvoert.

sync / async
Synchroon: stappen wachten op elkaar. Asynchroon: een taak kan later
afronden; dit staat los van de request-rate die k6 genereert.

Get-Content -Raw
Leest heel traffic.js als één tekstblok.

| en docker run -i
De PowerShell-pipe stuurt het JavaScript naar de invoer van de container.
-i houdt die standaardinvoer open.

grafana/k6 run -
Start k6 en leest het script van standaardinvoer ('-' betekent stdin).

--once
Voert één iteratie uit; geschikt als smoke test.

-e TARGET_URL="..."
Geeft het testadres door als omgevingsvariabele aan de container.
In traffic.js wordt dit via __ENV.TARGET_URL gelezen.

--rm
Verwijdert de Docker-container zodra de opdracht afgelopen is.

HPA
Horizontal Pod Autoscaler. Regelt het aantal applicatie-Pods op basis
van CPU of andere opgegeven metrics.
